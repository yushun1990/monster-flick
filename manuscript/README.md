# 正文协作与审稿流程

`manuscript/` 只保存小说正文；世界观、人物、专项设定与 Canon 继续放在 `docs/`。

## 目录约定

```text
manuscript/
  README.md
  01-tianxia-hunting/
    001-city-beyond-walls.md
    002-....md
```

- 一级目录按篇章/阶段编号。
- 章节文件按正文顺序编号。
- 正文只有一份，不建立 `draft/`、`final/` 两套副本，避免分叉。

## 章节状态

每个章节文件顶部用 YAML front matter 记录状态：

- `draft`：正在创作，尚未交给用户审阅。
- `review`：已整理成可读版本，等待用户批注/审批。
- `revision`：正在根据批注修改。
- `approved`：用户已明确批准本章内容；原则上只允许修正错字、标点等非内容问题。
- `final`：已合并到 `main`，视为当前正式正文。

状态只允许按以下主流程推进：

```text
draft -> review -> revision -> review -> approved -> final
```

如果 `approved` 或 `final` 后需要实质性改写，必须重新开 review 分支，并把状态退回 `review`。

## Git 审稿机制

每一章或一组紧密连续章节使用独立审稿分支，例如：

```text
review/tianxia-hunting-ch01
```

并创建 Draft Pull Request。

推荐审稿方式：

1. 在 PR 的 **Files changed** 中对具体行添加评论；这是首选方式，评论天然绑定原文位置。
2. 如果需要直接改文，也可以编辑审稿分支上的 Markdown，并在原文后加入批注块。

批注块统一写法：

```md
> [!NOTE]
> 批注：这里的动作不成立，范野此时不会主动暴露身份。
```

也可以直接写很短的判断，例如“删掉”“太刻意”“节奏太快”“这句保留”。不要求审稿人提供改写方案。

## 审批规则

- AI 不得自行把章节标记为 `approved`。
- 只有用户明确表达“通过 / 定稿 / 可以合并 / 这一章批准”等意思，才能把状态改为 `approved`。
- `approved` 后，由 AI 做一次最终一致性检查；无新内容修改时再合并 PR。
- PR 合并进 `main` 后，将该版本视为 `final`。
- 未合并的 Draft PR 永远不属于正式正文。

## 批注处理

AI 修改时应：

1. 逐条理解批注，不机械只改被点名的一句；
2. 如果多条批注暴露出同一种叙事偏差，应全章一起修正；
3. 不删除尚未处理完的审稿意见；
4. 修改完成后回复对应 PR 评论并标明处理结果；
5. 有争议或无法同时满足的批注，保留评论并说明冲突，不擅自定案。

## Canon 与正文的关系

- `docs/CANON_CURRENT.md` 与专项 Canon 约束正文。
- `manuscript/` 中的正文一旦 `final`，它本身也成为事实来源。
- 后续设定如果与已定稿正文冲突，应优先发现冲突并显式修订 Canon 或重开正文审稿，而不是静默覆盖。
